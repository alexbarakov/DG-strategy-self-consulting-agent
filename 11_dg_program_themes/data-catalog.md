# Data Catalog

## What the board teaches
The catalog is treated as the flagship — and most over-sold — DG tool. One track traces the idea's evolution: three generations of catalogs, five driving trends (modern data stack, diverse data teams, new decentralized vision for governance, metadata lake, active metadata platforms) converging into "Data Catalog 3.0" = active metadata + metadata lake + community-led governance + AI-driven features and programmable bots. The critical track is blunter: catalogs "have become cluttered with features in search of additional value", and their benefits are often lower than creation-plus-maintenance costs — so either reduce investment, increase value, or both, by identifying which specific value drivers matter for *you*. The board tiers catalog capabilities into primary/secondary/tertiary features, lists the recurring implementation challenges (business users repelled by complexity, stewards not engaged, stale descriptions, trust erosion, hard-to-articulate value), poses six "complex questions vendors have no clear answers to", and packages all of it into a five-block brainstorming template with a phased rollout plan (pilot group → MVP for data power users → product release for business users).

## Key objects
- Catalog evolution: 3 generations; 5 trends; Data Catalog 3.0 → active metadata (emphasized), metadata lake, community-led governance, AI features, programmable bots
- Primary features: source connectors; business glossary; metadata enrichment/storage; report catalog; API; bulk labeling/classification; column-level lineage; keyword/NL search with recommendations; integrated ownership/stewardship role model
- Secondary: DQ status by object (DQ tool integration); automated PII identification; annotations and certification endorsement; customization; data sharing / access request workflow; DG adoption reporting
- Tertiary: collaboration (chat, comment, rate); metadata generation automation; impersonation/user settings; alerting and dependency triggers; approval flow; IDE / SQL-Python editor
- Primary value statements: faster find-and-understand = better TTM; cross-utilization of certified objects; faster onboarding; cleaner landscape; faster impact analysis; PII scanned and access audited; stewardship made visible; data culture growth
- Top challenges: too complex for business; can't engage business stewards or data professionals; insufficient/outdated metadata; lack of trust; Golden Path fragmentation; glossary as separate hard problem; expensive; budget justification; value articulation
- Tool selection criteria: core features fit, community/popularity, tech stack, low TCO, sizing, simple UI, architecture complexity, low initial investment, open system
- Implementation sequence: domain structure + metadata integration → critical-layer logic → lineage (DWH, key ETL) → limited metadata load → BI layer → ownership model → MVP to production → glossary terms → certification → launch for data pros → ML classification/sharing → second-priority lineage → adoption CustDev → launch for business

## From the course (Data Governance Fundamentals, 6 days)

### Generations, and what actually changed
- The class grew out of metadata-management tooling, then accreted object management, search, lineage and "research" blocks; hybrids followed — catalog fused with a DQ engine (Ataccama the popular RU example), plus the Talend / Soda / Monte Carlo / Great Expectations cluster on the catalog↔DQ-portal boundary. (course day 4, transcript)
- Vendor generation story, kept because the framing is useful, not because it's true: 1.0 (Oracle era) = inventories by and for IT, "a constant struggle for IT folks"; 2.0 (Hadoop era) = steward-powered inventories for top-down governance programs, hard to maintain, "catalogs steadily fell behind the rest of the data stack"; 3.0 (cloud warehouses) = programmable bots, end-to-end visibility, embedded collaboration, open by default. (course day 4, slides p.88 — vendor material, use critically)
- On the vendor's own generations table the author pencils question marks against exactly two 3rd-gen claims: the tool "replaces the data steward", and these catalogs are "design first, easy to use for business users". (course day 4, slides p.89)
- Where he thinks it actually goes: metadata hubs refreshing faster and reaching past marts (Kafka topics; now agents and skills, themselves assets needing ownership and links); active metadata as two-way bots; features aimed at raising *domain* maturity rather than centralising; knowledge graphs back as the context substrate handed to agents. (course day 4, transcript; slides p.90–92)
- On his own legacy: "we built a catalog before it was mainstream" — "fairly unsuccessful handicraft, looking at it from today". (course day 4, transcript)

### Economics and the buy trigger
- The trigger is a U-curve: more people first means faster value; then tech debt, a bigger lake, growth, misalignments and worse DQ turn it around. Track Time to Value (delivery minus committed date), detect its increase, start there. (course day 2, slides p.35; course day 4, slides p.27)
- Real number: at a large tech company, search-and-understanding losses attributable to the catalog use case measured ~7M RUB/month — "not that much" at that scale. Expect yours "average, not very sexy": you are multiplying minutes by headcount. (course day 4, transcript)
- Benchmark: an ad-hoc's data communication (find marts, find people, get caveats) averages ~3-4 hours; with a certified, documented catalog + assistant the target is ~15 minutes. Works as a case from ~100+ analysts. (course day 2, transcript)
- Measuring without telemetry: mine catalog logs for search sessions with start, end and a success criterion; for the *baseline*, parse help chats, isolate catalog-target threads, time how long finding an object takes today. (course day 2 and day 4, transcript)
- Pure "analyst efficiency" is usually NOT enough in big tech — hide the catalog under other initiatives (AI enablement, core layer, certification). The AI framing lands: an assistant answers correctly only over objects of the right quality with the right relations to metrics and terms. (course day 2 and day 4, transcript)
- Catalog value is hostage to self-service BI, data products, contracts, mesh, ownership and DQM, and unlocks as they mature; if maturity there is low, redirect the resource. Sharpest framing of the day: "the benefit of a data catalog is often lower than the cost of producing and supporting it." (course day 4, slides p.42–44)

### Build vs buy — the real arguments and the real prices
- "For 90% of companies the boxed solution is optimal." Its flaw is psychological — expensive licences in the moment — but the odds of value beat "permanently operating a half-written, crooked, lopsided catalog". (course day 4, transcript)
- The cost nobody prices in: open source and in-house both need a real dev team for years, "even with modern vibe coding", *plus* product work — CustDev and feature adoption. "As a rule, a luxury most companies can't afford." (course day 4, transcript)
- The open-source trap: a catalog has "the illusion of a very simple product" to data engineers and platform managers. Wire up DataHub and it honestly stores metadata and lineage — and gets bad adoption, being hard to navigate for anyone wider than developers. UX quality decides whether it becomes "the habitat of all analysts and engineers, the starting point of any operation with data" — exactly what everyone draws in the deck. Many such projects sit permanently on the edge of ineffectiveness. (course day 4, transcript)
- A peer's three-path table, reusable as-is: boxed = fast rollout, vendor support, no admin payroll / expensive now, redundant features, missing ones can take long. Open source = conditionally free, extendable / needs a team, "integration = dancing with a tambourine". In-house = only what you need, fits self-written systems / working functionality "can take years". (course day 4, slides p.30)
- When building is legitimate: one large fintech's requirement list was a flexible metadata model (many self-written tools to integrate), column-level lineage for impact analysis, freedom from an industrial solution's constraints, controllable enhancement cost. Caveat: "this is not a role model — it's the reality that company works in; you may not have that reality." (course day 4, slides p.28; transcript)
- Confluence-as-catalog fails on six counts (no storage sync, no certification, no lineage, no data↔metric↔methodology links, no checks, no adequate search) — but run the multiplier honestly: if all data people sit in one or two tight central teams, "the effect of the catalog is not that significant". If you need only lineage, deploy a library and build an internal impact-analysis tool — "a technical feature", not a product. (course day 4, slides p.31; transcript)
- RU pricing (practitioner in the room): base box with ~2 connectors, each extra connector ~1.5–2M RUB, stewardship and admin seats and instances licensed (business read unlimited) — tens of millions of RUB, "and with implementation it can cross 100M"; SaaS vs on-prem shifts it materially. And the core is licensed whole: only connectors and the DQ part are separable, and the bundled DQ is "very simplified". (course day 4, transcript)
- Vendor maturity test: does the vendor bring methodology — glossary process, default card templates — or a bare box? "We supply none of that, it all depends on the customer" is the red flag. On built-in AI the vendor's own leadership is sceptical ("more of a trend story"), while the deck offers "if you have a strong vendor you can wait 2-3 years, they'll get the AI-driven features right", posted with a raised eyebrow. (course day 4, slides p.49; transcript)
- Constraint to design for: the strictest bank infosec allows metadata only — no samples, no profiling, "data — goodbye, guys", so half the profiling/masking functionality may be unusable. In critical infrastructure open source is banned outright: "don't come to me with your handicrafts, give me a vendor who answers for the product." (course day 4, transcript)

### Choosing: criteria, RFP and vendor-proof scoring
- "All available vendor comparisons are corrupt" — made by vendors with dishonestly picked criteria (canonically, a vendor's own quadrant on which that vendor wins). (course day 4, slides p.29)
- The scoring artefact: Eckerson's "Data Governance Platform Evaluation Criteria" xlsx — weighted yes/no across DG Portal, Search, Decision Rights, Data Catalog (connect/discover/profile/tag/classify/secure/annotate/automate/audit) and Business Glossary — plus the author's Russian adaptation with a 0–10 weight column and a Policy & Compliance / Risk Management block added. (course day 4, slides p.33–34)
- Method: weight the criteria for *yourself* first; accelerate pre-scoring with an LLM; but "if you are really choosing, you need your own pilot results, not somebody else's scores" — use the LLM pass only to reach a shortlist of 2–3 to pilot. (course day 4, transcript)
- Criteria follow pains, not feature lists: hard to locate datasets → search over metadata, terms, classifications, plus certification; no trust → descriptions and tagging, auto quality score, lineage; don't know whom to ask → owner/expert on the card; impact analysis → column-level lineage with health scores and DQ integration; GDPR pain → private-data classification with scanning jobs, access management and monitoring. Where infosec is a sponsor, bake their cases in early — "solve their task and they'll meet you halfway on everything else". (course day 4, slides p.35; transcript)

### Filling metadata — the gates that work
- A large fintech: "no description — no prod deploy"; table-description quality grew 49%→86% in a year across ~7000 tables. The gate can sit on deploy or on scheduling — "you cannot put an object on a schedule if it has no description". Softener: pair the hard gate with an AI "generate description" button, so one click drafts it and the author edits and opens the PR calmly. (course day 4, slides p.48; transcript)
- The "what works, though it doesn't guarantee results" list: maximize automated filling ("no reason for anyone to fill keys for every individual dataset"); a federated-catalog API so domain catalogs push in; algorithmically pre-fill domain, stewards, tags; inherit descriptions up the lineage from data contracts; documentation entered in the flow of work via a CI/CD check that breaks the build; "don't boil the ocean" — curate the top 20% node objects (most queried, or used in the most-viewed reports); ownership culture with domain data partners carrying a KPI on completeness. (course day 4, slides p.47)
- The top-20% rule pairs with the core-layer program: compute candidates from query analysis, let each domain finalize the list, raise requirements on that layer only, lower them elsewhere, and monitor completeness separately for core vs the rest. (course day 4, transcript)
- Catalogs are not pre-design tools: "the catalog is not chosen as a place for pre-design", objects appear after they exist in the warehouse. Instead — a table-description block in every dev spec, parsed and auto-loaded once the entity exists; glossary drafts early, physical descriptions post-release; master documentation living where development happens (dbt-style docs-as-code). The trade-off to hold: completeness is best near the end of the process, but motivation to enter anything collapses after release. (course day 4, transcript)
- AI-generated metadata, per top vendors themselves: it creates "the feeling that you have everything", but quality demands human-in-the-loop review. What AI cannot produce is tribal-knowledge caveats — "for this metric take this mart and these fields, but not for that one, because X isn't accounted for". Posture: tag output "requires review", or run a bot pinging the owner. A Claude Code skill acting as a technical data steward closes exactly the deficit that historically killed half-empty catalogs. (course day 4, transcript)
- The catalog, not Excel, must master domains and roles, with alerts on re-assignment, or people wash out silently: "we discovered nobody had been tending a domain for half a year." Typical starting picture for sponsors (Purview audit): 4-45% of assets had owners, ~46-74% lacked classifications. (course day 3, transcript; slides p.24)

### Adoption mechanics — what makes people actually open it
- "Data catalogs are not for casual users — that's a fact"; a report catalog inside the data catalog doesn't work for business either, and on "do you deliberately turn your catalog into a report catalog?" the answer is "as a rule, the right answer is: don't". Target model: data catalog for data-product teams + data marketplace/portal for consumers, chatbot-style discovery as the plausible new UX. (course day 4, slides p.51; transcript)
- Where business *does* belong: park the self-service scenario — a user sees certified, described objects, clicks through to open them in the BI tool, and knows whom to contact. (course day 4, transcript)
- UX fragmentation is the structural risk: the catalog went wide and shallow, and the data team ends up supporting two of everything. Pick a golden path and switch duplicates off. Conversations — "don't believe the built-in messenger of a data catalog, it's self-deception". Knowledge base — pick one, and accept that some domain information is better left in the wiki. Querying — an in-catalog IDE is "definitely not something to aim for". (course day 4, slides p.52; transcript)
- Product metrics: WAU (not DAU/MAU — natural usage frequency is weekly), 80% penetration of the target persona; CSAT out-of-band every 3-6 months plus feature voting (in-product feedback gets tarnished by the latest bad experience); metadata completeness per object tier — % described, median characters in field descriptions, % term linkage, metadata age; % usage of certified objects. Metadata age is operational: at ~1 year mark descriptions stale and auto-task domain roles to re-review. (course day 4, slides p.53, 86; transcript)
- Adoption is a product problem — CustDev, collect problems, ship fixes. Highest-yield feature named: lineage × DQ integration, where an incident propagates downstream at column level and shows as a red/yellow status on the specific field inside the graph — "that raises the value of lineage considerably". Pointed outward, the same idea is reverse metadata: push the card into the BI dashboard, term lookups into the messenger, workflow alerts into channels. (course day 4, transcript; slides p.64–65)
- A catalog becomes a DG tool only when the steward has an equipped workplace in it: a task inbox for their domain, policies to approve, DQ checks to review, documentation to fill, access rights to re-review. (course day 1, transcript)
- Eckerson deployment-challenge survey, for calibration: tool complexity 42.6%, lack of user adoption 40.7%, lack of integration 37.0%, missing functionality 25.9%, missing data or objects 22.2%, no access to actual data 22.2%, users don't trust the information 11.1%. (course day 4, slides p.65)

### Relationship to DQ tooling, the glossary, compliance and querying
- Myth 1, catalog = DG tool. No tool embodies governance, because governance is roles, responsibilities, policies, procedures, controls and committees — "an organizational wrapper that in essence doesn't fit inside a data catalog". (course day 4, slides p.66; transcript)
- Myth 2, catalog = DQM solution. "The catalog's role is not quality control, but maximum dissemination of the results of that control." Catalogs are by nature bad DQM solutions and DQM solutions are mediocre, over-complicated catalogs. Concretely: the checker engine lives in the DQ portal; the *results* ship as a module inside the catalog, with incident review and time-to-resolution. A practitioner veto backs this — the catalog's engine is not built for high-performance checks, which killed the "DQ inside OpenMetadata" option in one enterprise evaluation. (course day 4, slides p.67; transcript)
- Myth 3, catalog = compliance solution. Compliance is first of all documentation and evidence; the catalog can help identify regulated data and raise awareness. In-catalog auditor cabinets exist but are "a very rare, niche story". (course day 4, slides p.66–69; transcript)
- Myth 4, catalog = query solution. Querying from the catalog is "not only redundant but quite risky" (performance, cost, security). "Integrating data-access workflows into a catalog rollout is the surest way to make the project long, costly and disappointing." (course day 4, slides p.75)
- The glossary is the hardest component and only nominally a catalog problem — the one part requiring active business participation. The author's own catalog has lived three years without one: "problematic, but we can't find a driver for it". Business isn't motivated to write definitions; analysts know the content but it is "mildly speaking not their priority" — the same pathology as ownerless corporate reference data in MDM. The "whole company speaks one language" pitch "looks a bit ephemeral"; lineage and core catalog features sell far better, and the glossary sits under "reserved for the mature". Evidence from the room: a company with two metrics, "sales" and "revenue", where nobody can say which is correct. (course day 4 and day 5, transcript; course day 6, slides p.100–101)
- Two practical notes: bulk Excel import/export of terms matters more than it sounds (business filters terminology offline and loads it back; the same mechanism hand-enriches lineage relations the parser missed), and policies belong in the catalog because "documents must not hang in the air" — a PII policy linked to all tagged PII assets can warn at query time. (course day 4 and day 5, transcript)

### Lineage reality
- Lineage is "certainly the most hyped element", and the slide answering it is a hairball graph of the whole mart/metric dependency set with one caption: "the phone-a-friend option is more reliable". (course day 4, slides p.56–57)
- He spent about an hour debating a central-bank CDO who held lineage is useless, and the honest conclusion is a question: who uses it and for what? "If you have logs — dig into them; you may discover nobody uses it", because upstream discovery happens elsewhere, another way. Self-disclosure: "our lineage is complex, badly visualized, and it seems we extract very little value from it in fact". (course day 4, transcript)
- So invest against two concrete jobs only: incident impact analysis, and pipeline/critical-path optimization — the latter now well served by agentic audits that produce recommendations without rewriting anything yet. (course day 4, transcript)
- What matters in lineage functionality, in his own ordering: (1) breadth of native integrations, (2) column-level linkage, … (N) "…beauty?" — the joke is the point. (course day 4, slides p.64)
- The one hard requirement is column-level. "Without column-level lineage everything is rather sad" — and it is the enabler for SQL-writing agents, letting an agent see how objects connect through which columns and build correct joins across marts. Pair it with a base of proven successful joins. (course day 4, transcript)
- Vendor patterns worth copying if you build: issue detection on the graph; business-term / domain lineage (every asset touched by the 'PII' term); lineage annotated with DQ scores at table+attribute level; filtering by a single field. (course day 4, slides p.60–63)

### ROI math and how to discount vendor claims
- Every vendor calculator makes one move: assume a productivity percentage, multiply by headcount and salary. Collibra's: 23% for BI/data analysts and data scientists, 5% for report/app developers and enterprise architects, 26% for integration engineers, DG professionals and stewards, 27% for compliance professionals. Plug in 120 + 120 + 45 people at $180k/$150k/$150k and it returns $8.379M annual gain, 102,960 person-hours saved, 9.3× three-year ROI against a $2.48M TCO. (course day 4, slides p.80–86 — marketing numbers, use critically)
- Forrester's TEI for Alation is more instructive because the assumption chain is visible: $3.8M benefits PV vs $813K costs PV — analyst productivity from shortened discovery $2.74M, business-user self-service $584K, data engineers $165K, faster onboarding $286K — built on 75 analysts, "70% of an analyst's work affected by the tool", 70% reduction in time to serve business users, 50% productivity capture, 10% risk adjustment; onboarding 2 months cut by 50%. (course day 4, slides p.80–86 — marketing numbers, use critically)
- The author's discount: "we can't verify the numbers, but the evaluation logic is worth copying". You are simply asked to believe 23% and derive the rest. Realistically expect 5-7% provable. (course day 4, transcript)
- The correction picky finance will make, so make it first: a productivity improvement does not convert into output. "People just start going for coffee more often, or chatting with colleagues in the kitchen." (course day 4, transcript)
- The one multiplier worth stealing wholesale is onboarding: an analyst reaches full productivity in three months; with a well-described catalog, in two. The same method as homework: 120 analysts × 2.4M RUB × 23% plus three more role groups = 92.3M RUB benefit vs 35M RUB cost — with the warning that "the productivity % is a huge zone of speculation". Calibration from his own honest calculation: the entire DG slice produced a monthly effect that looked very small against company scale — he weighed whether to publish it at all (figure withheld here). Compare any vendor benefit model against that shape. (course day 6, slides p.20; transcript)

### Peer evidence: what worked and what was dropped
Seven large tech companies from the author's own interviews; employers anonymized. Full board in `dg-kitchen-research.md`. (course day 4, slides p.87; transcript)
- **Ride-hailing arm of a large tech group — bought, fastest rollout.** Until 2019 a self-written dbt-like solution with YAML docs-as-code, judged "inconvenient"; OpenMetadata was raw; they needed it faster and didn't wait. Chose Alation — the open push API was decisive. Live in under 6 months with 3 part-time people (manager, developer, analyst).
- **Marketplace — tested and dropped.** DataHub tested, went no further. Documentation lives in the wiki and "lands as tech debt". Considering a documentation gate in the deploy flow; compensating today with a support chat in every domain.
- **Fintech — own product, dynamic.** Develops fast on security and metadata loading, but domains are poorly laid out, the glossary was never built for lack of domain involvement, and the concept "the catalog is not for input" has been revised — they are launching edit.
- **Social network — open source, early stage.** Started on DataHub; also looked at OpenDataDiscovery ("all sensible, but few contributors") and rejected OpenMetadata for having no push approach. PII field marking started; lineage not done yet.
- **Job board — custom on Atlas, thin ownership.** Own build after a commercial pilot that didn't land. Only 30% of objects have owners; audience of 30 analysts. Since then they engaged a commercial vendor for a second attempt — "if they found drivers for a second run, they accumulated investment reasons".
- **Delivery company — open source, view-only, thin adoption.** Evaluated Collibra and OpenMetadata, deployed DataHub, in prod only from October. Features: KPI definitions, search, impact assessment, lineage, DQ results, tag validations, column-level usage, ownership. Target power users 900, monthly actives 90. All input via GitHub and integrations.
- **Large tech company (the author's) — custom, vendor lock refused.** "We can't afford dependence on a vendor — open source only." What mattered: custom integrations and search quality. Base functionality first (marts and detail layer, git and Jira integration, checker info, metadata entry, search); MVP in one quarter with 1 front-end and 2 Go backend engineers, then a team of up to 10 through year two.
- His read of the board: DataHub in 2 of 7, two more custom on open-source bases, "no extra information here" beyond the number that stands out — 30% of objects with owners on a 30-analyst audience is "a rather sad current situation". (course day 4, transcript)

## Maturity signals
- **No catalog, and honestly fine.** Docs in the corporate wiki, discovery via per-domain support chats. One respondent's argument stands: "everyone works inside their own domain and doesn't go outside — chats are enough for us." Legitimate when all data people sit in one or two tight central teams. (course day 2, slides p.54; course day 4, transcript)
- **Catalog exists, ownership thin.** 4-45% of assets with owners and 46-74% without classifications on a Purview audit; a custom build with owners on 30% of objects and an audience of 30 analysts; PII marking just started, lineage not built. The stage where "the tool exists = the process doesn't". (course day 3, slides p.24; course day 4, slides p.87)
- **In production, but read-only and thinly adopted.** All input via git and integrations, UI view-only; 900 target power users against 90 monthly actives — ~10% penetration against the 80%-of-target-persona benchmark. (course day 4, slides p.87 vs p.53)
- **Documentation gates in place.** "No description — no prod deploy" or "no schedule"; description quality moving 49%→86% across ~7000 tables; algorithmic pre-fill of domain, stewards, tags; descriptions inherited up the lineage from contracts. (course day 4, slides p.47–48)
- **Catalog as the governance surface, not the reference book.** It masters domains and roles with alerts on re-assignment; the steward has a workplace inside it; certification status changes emit events other services consume; DQ results are a module; % usage of certified objects tracked per domain. (course day 1 and day 3, transcript; course day 3, slides p.119; course day 4, slides p.53)
- **Active metadata.** Bots go to owners on triggers and ask them to fill, certify or archive; metadata age auto-tasks re-review at ~1 year; reverse metadata pushes the card into BI and the messenger; the metadata lake extends past marts to Kafka topics, agents and skills. (course day 4, slides p.65, 88–92; transcript)
- **Cross-cutting: the glossary arrives last, if at all.** In big tech "the glossary simply doesn't take off"; a three-year-old catalog without one is a late-maturity target, not an entry ticket you failed. (course day 5, slides p.28; transcript)

## Anti-patterns
- **The platform team hides behind the data catalog.** One of the four key findings of the peer research: the catalog is used to avoid the hard data-management questions — ownership, criticality, contracts, role model. Buying a tool reads as progress and defers the org work indefinitely. (course day 1, slides p.117; course day 6, slides p.99)
- **The burnt desert.** You pay a lot of money and get ghost towns of empty field descriptions; trust drops and the tool degrades into a mere search box "in the best case". (course day 4, slides p.40, 44, 46)
- **Coverage as a vanity metric.** "% of objects described" with no tiering hides everything that matters; replace with completeness per object tier, median characters in field descriptions, % term linkage and metadata age. (course day 4, slides p.53; transcript)
- **The open-source trap.** A catalog looks like "a very simple product" to data engineers, so it gets built — and ends up an ugly metadata store that never becomes the starting point of data work. (course day 4, transcript)
- **Golden-path fragmentation.** A built-in messenger nobody uses, a second knowledge base competing with the wiki, a second querying surface. "It's self-deception." (course day 4, slides p.52)
- **Catalog as report catalog for business users.** Doesn't work; consumers need a marketplace/portal with certified content. (course day 4, slides p.51; transcript)
- **Catalog as the DQ engine.** The engine isn't built for high-performance checks — integrate, don't merge. (course day 4, slides p.67; transcript)
- **Bolting data access onto the catalog rollout.** "The surest way to make the project long, costly and disappointing." (course day 4, slides p.75)
- **The bare-box vendor.** No methodology, no glossary process, no default card templates: "it all depends on the customer". (course day 4, transcript)
- **Believing the generation-3 pitch.** The two claims the author question-marks are exactly the two most-sold: "replaces the data steward" and "design first, easy to use for business users". (course day 4, slides p.89)
- **Catalog as a pre-design workspace, or Excel as the master of domains and roles.** Neither has been seen working: objects land in the catalog after they exist, and role registries kept outside it let people wash out silently — "nobody had been tending a domain for half a year". (course day 3 and day 4, transcript)
- **AI-filling everything without owner confirmation.** You get "the feeling that you have everything" and lose exactly the caveats that made the documentation worth reading. (course day 4, transcript)
- **Buying before the surrounding maturity exists.** If self-service BI, data products, contracts, ownership and DQM are immature, the resource belongs there. (course day 4, slides p.42–45)

## Questions to ask before buying or building

**About your company, before any demo**
- Do you have enough *aggregate maturity* to launch a catalog and get value from it at all? (course day 4, slides p.43)
- Do you have enough *aggregate practical value* in it to expect analysts and engineers to keep coming back? (course day 4, slides p.50)
- Do you involve business — and if yes, what do you show them so they don't flee in horror? (course day 4, slides p.42)
- How should interfaces differ for business roles vs data roles to actually grow engagement? (course day 4, slides p.54)
- What is your baseline search time today, and how will you measure it a year from now, given nobody has that kind of time tracking? (course day 4, slides p.42; transcript)
- Which single golden path are you choosing for conversations, knowledge base and querying — and what are you switching off? (course day 4, slides p.52)

**About scope and duplication**
- Lineage: where do you stop with integrations, and who actually needs it and why? (course day 4, slides p.42)
- Your report catalog duplicates your analytical portal, which is the one users find convenient. What do you do about that? (course day 4, slides p.42)
- What do you do with the burnt desert instead of field descriptions, and how do you grow oases there? And AI-made descriptions — does anyone actually need them? (course day 4, slides p.42, 46)
- What do you do with the redundant functions vendors stuffed in "for good measure", including the data-management modules inside BI systems? (course day 4, slides p.42)
- How do you run a glossary if business won't step into the steward role and the technical custodian lacks the business context? (course day 4, slides p.42)

**To the vendor, in the room**
- Do you bring methodology — glossary process, target processes, default object-card templates — or a bare box? (course day 4, transcript)
- Is the core licensed whole, or can modules really be switched off? What exactly is priced separately: connectors per source type, steward seats, admin seats, instances? (course day 4, transcript)
- Is there an open push API — can our teams and our agents write metadata in, not only read it out? This was the deciding criterion in the fastest peer rollout on the board. (course day 4, slides p.87; transcript)
- What still works if our infosec allows metadata only — no samples, no profiling against live data? (course day 4, transcript)
- Show me your comparison chart's criteria and who picked them. "All available comparisons are corrupt." (course day 4, slides p.29)

**If you are building**
- Who owns the UX, and for how many years? The hidden cost is not the metadata store, it is the product work. (course day 4, transcript)
- Can you fund a permanent team, given that catalogs lose the fight for engineers and "every catalog shows a fading trend"? (course day 2, transcript)
- If all you actually need is impact analysis, would a lineage library plus an internal graph tool be enough — without a catalog product at all? (course day 4, transcript)
